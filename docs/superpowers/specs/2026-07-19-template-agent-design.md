# Template Agent — client-report auto-fill from an uploaded template (2026-07-19)

**Status:** Design / for review.
**Goal:** A user uploads a client's report **template** (or a filled sample), the system learns its structure once, and thereafter auto-fills that structure from the FieldSight item store for any (site, period) — producing a finished report in the client's own format. The structure is extracted with **LandingAI ADE** (Agentic Document Extraction, DPT-2); the fill is an **agentic flow** over the item store.

**Repos:** fieldsight-pipeline (ADE integration, template + mapping storage, agentic fill, docx render — all in the non-VPC report path) + fieldsight-ui (upload, mapping review, generate/download).

---

## 1. Problem & motivation

Construction clients each want their daily/weekly report in **their own format** (headings, tables, fields, branding). FieldSight already holds the underlying facts in its **item store** (Aurora: `topics`, `action_items`, `findings`, `safety_observations`, `topic_photos`, + the weather block from the site-location-weather spec) and generates its own daily report — but not in an arbitrary client's layout. Today that reformatting is manual per client, per period.

The user's ask: upload a client report → analyze its **structure** → **agentic flow auto-fills** reports in that structure. Accept both a **blank template** and a **filled sample** (ADE's zero-shot parsing reads either).

---

## 2. Goals / non-goals

**Goals**
1. Upload a client report template **once** per client; extract its structure with ADE and store a reusable **template + field-mapping**.
2. A human **reviews/edits the mapping once** (which FieldSight data feeds which template slot) before it is trusted — AI mapping is not always right, and a wrong mapping would poison every future period.
3. Auto-fill that template for any (site, period) via an **agentic flow** over the item store.
4. **Pixel-faithful output for `.docx`** templates (fill into the real file), a **structure-faithful regeneration** fallback for non-`.docx`.
5. Near-zero cost: ADE runs **once per template** (not per report); fill reuses the existing Claude report path.

**Non-goals**
- Real-time collaborative editing of the output document (download + edit externally is fine).
- Pixel-faithful output for PDF/scanned templates (fallback is structure-faithful regeneration — see §3.5 / D3).
- Replacing FieldSight's own native daily report — this is an *additional* client-format output, same facts.
- Learning a template from many samples / fine-tuning — one uploaded artifact, zero-shot (D6).

---

## 3. Design

### 3.1 Entity: `report_template` (one per client/company, reusable)
Stored once at upload, reused every period:
- the **original artifact** (the uploaded `.docx`/PDF, in S3);
- the **ADE structure schema** (sections, headings, tables, placeholders, each with visual grounding — page + bounding box — and a confidence score);
- the **field-mapping** — an ordered list of `{ slot, kind, source, instruction, confidence }` where `slot` is a template location (section heading / table / placeholder token), `source` is a FieldSight item-store data source (see §3.3), and `instruction` is how to fill it. Produced by the agent (§3.2 stage 2), **edited + confirmed by a human**, then frozen for reuse.
- scope: which company (and optionally which sites) this template serves.

### 3.2 The agentic flow (four stages)

**Stage 1 — Analyze (ADE, once per template).**
Upload → send the artifact to **LandingAI ADE** (`ade-python`, DPT-2). ADE returns a structured, visually-grounded parse of the document: chunks typed as heading / paragraph / table / field, with page + coordinates + confidence. Works zero-shot on a blank template *or* a filled sample (a filled sample additionally reveals example content/style per slot, used to sharpen the mapping). Runs in a **non-VPC** function (ADE is an external HTTPS API).

**Stage 2 — Map (agent proposes, human confirms).**
A Claude call takes the ADE schema + a catalogue of FieldSight data sources (§3.3) and proposes the field-mapping: for each template slot, the best-matching source + a fill instruction + a confidence. The UI shows the mapping **beside the template** (using ADE's bounding boxes to highlight each slot) for the user to **edit/confirm**. Low-confidence slots are flagged. The confirmed mapping is stored on the `report_template`. This is the one human-in-the-loop gate; everything after is automatic per period.

**Stage 3 — Fill (per (site, period), agentic).**
For a requested (site, period): for each mapped slot, pull its FieldSight source data for that window; then
- **structured slots** (tables, single fields — e.g. action-items table, weather field) are filled **deterministically** from the item store (no LLM);
- **narrative slots** (prose sections — e.g. "Site progress summary") are generated by a **per-section Claude call** grounded in the retrieved item-store data (RAG over that period's topics/findings), with an instruction to use only supported facts.
Per-section (not one giant prompt) keeps each generation focused and auditable, mirroring the repo's existing extraction pattern.

**Stage 4 — Render.**
- **Primary (`.docx`)** — `python-docx` (already in the stack via the DocxLayer, BUG-24) opens the **original template** and writes each slot's filled content into its real location (placeholder token / content control / table cell / under-heading paragraph), preserving 100% of the template's layout, styles, and branding. Output = the client's own document, filled → pixel-faithful.
- **Fallback (non-`.docx`)** — no source file to fill into, so **regenerate**: emit a new document that follows the ADE structure (same section order/headings/tables/fields) in FieldSight's own styling. Structure-faithful, not pixel-faithful.
Output `.docx` (+ optional PDF) lands in S3 under the reports prefix, downloadable like the existing Word reports.

### 3.3 FieldSight data sources for mapping (the item store)
The mapping's `source` is one of the item-store facts the pipeline already produces (Aurora, read in-VPC by the org-api / report path), scoped to (site, period):
- `topics` (title, summary, category, time_range, participants)
- `action_items` (text, responsible, deadline, priority, status)
- `findings` (observation, domain, severity, entity, recommended_action, programme-impact)
- `safety_observations` (observation, risk_level, location, status)
- `topic_photos` (image + caption)
- `weather` block per (site, date) — from `2026-07-19-site-location-weather-design.md`
- site/company metadata (name, address, client, period dates)
Each is exposed to Stage 3 as a typed accessor; the mapping picks which feeds which slot.

### 3.4 Where it runs (VPC / integration)
- **ADE + the fill Claude calls are external HTTPS → non-VPC** (the repo's report path — `ReportGeneratorFunction`/`ExtractSessionFunction` — is already non-VPC with egress; this feature lives there or in a sibling non-VPC function). ADE runs once at upload; fill runs per period.
- **Item-store reads are in-VPC (Aurora).** The period's data is read in-VPC and supplied to the non-VPC fill step (the same split the site-location-weather spec uses), or read via the org-api. No in-VPC function makes an outbound call (BUG-36).
- The `.docx` render is pure `python-docx` (no network) and can run wherever the fill assembles the content.

### 3.5 Human-in-the-loop & correctness
- The **mapping** (Stage 2) is human-confirmed once — the durable correctness gate.
- ADE **confidence** + visual grounding surface low-confidence structure for review at analyze time.
- Narrative fill (Stage 3) is instructed to use only item-store-supported facts (no fabrication); the output is a **draft** the user reviews/edits before sending to the client (this system never sends anything to a client automatically — out of scope).

### 3.6 Storage
- Original artifact + rendered outputs: **S3** (reports prefix).
- `report_template` (schema + mapping + scope): a new Aurora table (mirrors the item-store's Aurora home) so the in-VPC pipeline and org-api can read it.
- Rendered report metadata: alongside existing report records.

## 4. Decisions

- **D1 — Structure extraction: LandingAI ADE (DPT-2).** Zero-shot, visually grounded, confidence-scored; handles `.docx`/PDF/scanned/complex tables; `ade-python`; 1000 free credits (credits = pages×0.5), one-time per template. (§3.2 stage 1)
- **D2 — Template is a stored, reusable entity with a human-confirmed mapping.** Analyze once, confirm mapping once, reuse every period. (§3.1/§3.2)
- **D3 — Render: `.docx` fill-into (pixel-faithful) primary; non-`.docx` structure regeneration fallback.** (§3.2 stage 4 / user decision 2026-07-19)
- **D4 — Fill is agentic + per-section:** deterministic for structured slots, grounded Claude per narrative slot. (§3.2 stage 3)
- **D5 — Non-VPC for ADE + fill (external HTTPS); in-VPC only reads Aurora and hands data across.** (§3.4)
- **D6 — Zero-shot from one artifact** (blank template or filled sample); no multi-sample training. (§2)
- **D7 — Output is a reviewable draft; nothing is auto-sent to a client.** (§3.5)

---

## 5. Risks / open questions

- **ADE extraction quality on real client templates** — the whole flow rests on ADE producing a usable structure. **De-risk with a Phase-1 spike** (§6): run a real client `.docx` + a real PDF through ADE with the free tier, inspect the schema, before building the full flow. If quality is poor for a format, that format stays fallback-only.
- **`.docx` fill placement when the template has no explicit placeholders** — a template that is just headings + empty tables needs the agent to decide *where* under a heading / which table/row to write. The mapping (Stage 2, human-confirmed) pins this per slot; still the hardest engineering part.
- **Data governance** — uploading a client template (a filled sample may carry client content) to LandingAI. One-time per template; ZDR/BAA available on ADE paid tiers if required. Surface this to the user before enabling for a company.
- **Scope creep** — this is a sizeable subsystem; keep Phase 1 to *analyze + mapping review* (prove ADE + the entity), Phase 2 to *fill + render*.
- **Cost drift** — ADE is per-page and per-template only; fill reuses the existing Claude budget. Watch only if templates are huge or re-analyzed often.

---

## 6. Phasing (for writing-plans)

- **Phase 0 — Spike (de-risk):** obtain an ADE free key, run 1–2 real client templates (a `.docx` and a PDF) through `ade-python`, inspect the returned structure/confidence. Decide go/no-go and which formats are primary vs fallback. Small, throwaway.
- **Phase 1 — Template intake + mapping:** upload UI, ADE analyze (non-VPC), `report_template` table, agent-proposed mapping, human review/confirm UI (bounding-box overlay). Deliverable: a stored, confirmed template.
- **Phase 2 — Fill + render:** per-(site,period) agentic fill, `.docx` fill-into render + non-`.docx` fallback, S3 output + download. Deliverable: a finished client-format report.

Each phase is its own plan.
